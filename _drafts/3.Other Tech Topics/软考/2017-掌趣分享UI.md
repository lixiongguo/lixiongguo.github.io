### MVC框架与PureMVC

UGUI 默认写法容易把「节点引用、点击回调、协议回包、界面刷新」全堆进一个 `MonoBehaviour`，界面一多就变成互相 `Find` / 直接调对方方法。掌趣侧自研 UI 框架的目标是：

> **美术拼 Prefab，程序只绑定逻辑**——仿 Android 的 Activity / View 分层思路，对 UGUI 做二次封装，并用 **PureMVC** 把数据、界面、业务命令拆开。

#### 为什么要 MVC

| 直接写 UGUI | 加 MVC / PureMVC 后 |
|:---|:---|
| 一个 Panel 脚本既找节点又请求又改数据 | View 只负责显示与输入 |
| Panel A 直接 `GetComponent` 调 Panel B | 通过 Notification 通信，不互相持有 |
| 换皮 / 改布局常改程序代码 | Prefab 可独立改，逻辑靠路径或绑定表挂接 |
| 难测、难复用 | Proxy / Command 可单测业务，Mediator 可复用 |

协作上：美术出界面 → 约定控件命名或绑定表 → 程序写 Mediator / Command，不必为挪按钮改业务代码，UI 迭代周期明显缩短。

#### 经典 MVC 与 PureMVC 的对应

```
        ┌────────── Notification / Facade ──────────┐
        │                                           │
        ▼                                           ▼
   ┌─────────┐    操作数据     ┌─────────┐    更新UI    ┌──────────┐
   │ Command │ ─────────────► │  Proxy  │ ─Notify───► │ Mediator │
   │(业务)   │ ◄── Retrieve ─ │ (Model) │             │ (View)   │
   └─────────┘                └─────────┘             └────┬─────┘
        ▲                                                  │
        └────────── 用户操作发 Notification ───────────────┘
```

| MVC | PureMVC 角色 | 职责 |
|:---|:---|:---|
| **Model** | **Proxy** | 持有 VO / 缓存、读写协议数据；**只发不收** Notification |
| **View** | **Mediator** + ViewComponent（UGUI Prefab） | 监听控件事件 → 发通知；收通知 → 刷新界面 |
| **Controller** | **Command** | 无状态业务流：开界面、发请求、串联多个 Proxy |
| **统一入口** | **Facade**（单例） | 注册 Proxy / Mediator / Command，`SendNotification` |

通信载体是 **Notification**（名称 + body + type），Observer 由 View / Controller 登记；模块之间尽量不直接引用，降低耦合。

#### 在 Unity 里的落地约定

结合 UGUI 与「仿 Android」封装，项目里大致约定：

1. **ViewComponent**：Prefab 上的薄壳（或自动绑定生成的控件引用），**不写业务**；可类比 Android 的布局 XML + `findViewById`。
2. **Mediator**：不继承 `MonoBehaviour`，持有 ViewComponent 引用；`OnRegister` 里绑按钮，`listNotificationInterests` 声明关心的消息。
3. **Proxy**：如 `BagProxy`、`BagProxy`，封装协议与本地缓存；数据变更后 `SendNotification(xxx_CHANGED)`。
4. **Command**：如 `StartupCommand`、`OpenPanelCommand`、`SubmitXxxCommand`；复杂流程放这里，避免 Mediator 膨胀。
5. **Facade**：游戏启动时注册映射；打开界面 = `SendNotification(OPEN_XXX)`，由 Command 加载 Prefab 并 `RegisterMediator`。

示意（登录成功刷新主界面）：

```
LoginMediator: 点击登录 → SEND LOGIN_REQUEST
LoginCommand:  调 AuthProxy 请求 → 成功则 SEND LOGIN_SUCCESS
AuthProxy:     写入玩家数据 → SEND PLAYER_DATA_CHANGED
MainMediator:  收到 PLAYER_DATA_CHANGED → 刷新头像 / 昵称
```

#### 与「纯 MVC」的差异（实践注意）

| 点 | 说明 |
|:---|:---|
| **Proxy 不收通知** | 数据层保持独立，避免 Model 依赖 View |
| **Mediator 可读 Proxy** | 简单刷新可直接 `RetrieveProxy`；复杂编排仍应走 Command |
| **Notification 字符串** | 建议集中常量表，避免拼写错误与魔法字符串满天飞 |
| **生命周期** | 关界面要 `RemoveMediator`，避免监听残留；对象池复用时注意重绑 |
| **性能** | 高频 UI（伤害飘字等）不必硬套完整 PureMVC，可用轻量事件或直接驱动 |

#### 小结

自研框架 = **UGUI 工程化封装（美术 / 程序分工）** + **PureMVC（数据 / 界面 / 命令解耦）**。前者解决「谁改 Prefab、谁写逻辑」；后者解决「界面多了怎么通信、业务往哪放」。MMORPG 这类面板多、协议多的项目，比单脚本堆逻辑更可持续。

## UGUI工程化封装

PureMVC 解决的是「业务怎么拆」；**UGUI 工程化封装**解决的是「界面资产怎么生产和挂接」——让美术改 Prefab、程序改逻辑尽量互不踩脚。思路借鉴 Android：布局归布局，逻辑通过控件引用绑定，而不是在每个 Panel 脚本里手写 `transform.Find`。

### 要解决什么问题

裸用 UGUI 时，常见工程问题：

| 问题 | 后果 |
|:---|:---|
| 脚本里大量 `Find("xxx/yyy")` | 改层级就炸；字符串难重构 |
| Prefab 上挂满业务 `MonoBehaviour` | 美术动节点易丢引用 / 改坏逻辑 |
| 打开关闭、层级、遮罩各自为政 | 多面板叠层混乱、内存难管 |
| 控件用法不统一 | 按钮音效、灰态、红点各写一套 |

工程化封装的目标一句话：

> **Prefab = 布局资源；运行时由框架加载、绑定、驱动——程序不碰节点树细节，美术不碰业务代码。**

### 仿 Android 的分层

| Android | 本框架对应 | 职责 |
|:---|:---|:---|
| XML Layout | UGUI Prefab | 只描述结构、锚点、样式 |
| `findViewById` / ViewBinding | 控件绑定（命名约定或绑定表） | 把 Button / Text 等变成强类型字段 |
| Activity / Fragment | Panel + Mediator | 生命周期、显示隐藏、与玩法对接 |
| 系统 Window 管理 | UIManager（栈 / 层级） | 打开、关闭、互斥、返回键 |

### 封装通常包含什么

```
美术：Prefab（命名规范 / 绑定标记）
        │
        ▼
  代码生成或运行时绑定  →  ViewComponent（纯控件引用，无业务）
        │
        ▼
  UIManager 加载 / 入栈 / 分层
        │
        ▼
  Mediator 订阅点击与 Notification  →  刷新显示
```

1. **控件绑定**
   - 约定节点名（如 `btn_ok`、`txt_name`），或 Prefab 上挂绑定组件勾选字段；
   - 启动或导入时生成 View 类，避免手写 `Find`；
   - 绑定失败尽早报错（缺按钮比运行到一半空引用好查）。

2. **Panel 生命周期**
   - 统一 `Open` / `Close` / `Show` / `Hide`（及可选 `OnPause`）；
   - 打开：加载 Prefab → 绑定 → `RegisterMediator`；
   - 关闭：反注册、回池或销毁，防止监听泄漏。

3. **UI 层级与栈**
   - 按层排序：HUD / 功能面板 / 弹窗 / 顶层 Tip；
   - 栈式管理：后开盖前开，关闭自动露出下层；
   - 全屏面板可隐藏 3D 相机或下层 Canvas，降 Overdraw。

4. **资源与实例化**
   - 按名或 ID 加载（Addressables / AssetBundle）；
   - 高频界面对象池复用，打开只重置数据不反复 `Instantiate`；
   - 与 PureMVC 的 `OpenXxxCommand` 对接：业务只发「打开某某界面」，不散落 `Instantiate`。

5. **通用控件约定**
   - 统一按钮点击音效、禁用态、二次确认；
   - 红点、货币条、空状态等做成可复用组件，业务只填数据。

### 协作流程（工程化的收益）

```
策划出需求 → 美术出 Prefab（按规范命名）
                ↓
         绑定 / 生成 View 类
                ↓
         程序写 Mediator + Command
                ↓
         联调：改布局少动逻辑，改玩法少动 Prefab
```

相对「一个脚本既拼界面又写玩法」：

- **美术**可独立改锚点、换皮、加装饰节点（不破坏约定控件名即可）；
- **程序**只关心 View 暴露的字段与消息，不维护节点路径；
- **迭代**时 UI 改动与协议 / 玩法改动可并行，缩短合入冲突。

### 与 PureMVC 的关系

| 层 | 解决什么 |
|:---|:---|
| **UGUI 工程化封装** | Prefab 怎么规范、怎么绑、怎么开关联、怎么分层 |
| **PureMVC** | 绑好之后，点击 / 协议 / 多界面刷新怎么解耦 |

没有工程化封装，PureMVC 的 Mediator 仍会陷入 `Find` 和生命周期乱写；没有 PureMVC，封装只解决了「界面壳子」，玩法逻辑仍会堆在 Panel 脚本里。两者一起，才形成「美术拼界面 + 程序绑定逻辑」的完整闭环。
