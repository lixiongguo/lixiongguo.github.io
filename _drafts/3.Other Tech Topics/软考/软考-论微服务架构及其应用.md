# 论微服务架构及其应用

## 摘要

2023 年 3 月至 2024 年 1 月，我参加了某市智慧农机作业服务平台的建设，担任系统架构师，负责总体架构、服务划分和关键方案评审。平台面向农机合作社与种植户，提供地块管理、作业任务调度、装备接入、轨迹与质量监测以及费用结算。终端数量大、作业季流量集中、结算规则调整频繁，继续沿用单体架构时，一次发布就要全量停机，轨迹写入的热点也无法单独扩展。项目改用微服务架构，按业务能力拆成用户权限、地块、任务、设备接入、轨迹质量和结算等服务，各服务独立进程、独立数据库，经网关统一接入，跨服务通知和流量削峰交给消息队列。实施中重点处理了结算一致性、上报突发和拆分过细三个问题。上线后核心服务可以按周独立发布，作业高峰期轨迹接入保持稳定，任务完成与结算入账达到最终一致。实践说明，微服务是否有效，取决于服务边界是否按业务能力划分，以及一致性、流量和观测是否一并设计。

## 正文

### 一、项目概述及本人工作

某市农业农村部门需要一套面向合作社和种植户的作业服务平台，把分散的农机调度、地块档案、田间作业记录和补贴结算放到同一业务链条上。建设前，调度靠电话和表格，轨迹存在各装备厂商自己的平台里，结算与作业事实对不上。业主希望平台能登记地块、下发任务、接收位置与工况、评定作业质量，并据此生成结算单。

系统有四类用户：管理部门、合作社调度员、农机手和种植户。功能上分为门户与权限、地块与空间数据、作业任务、设备接入、轨迹与质量评估、费用结算、消息通知。非功能上有三点压力。一是作业季白天上报密集，单台装备数秒一条轨迹，全市同时在线装备可达数千台，接入侧要扛住突发流量。二是任务、轨迹和结算分属不同业务规则，结算口径一个作业季会调几次，不能因为改结算就重新发布整套系统。三是地块数据带空间查询，轨迹数据写多读少，两类数据放在同一库里会互相拖累。

我作为系统架构师，参与了需求结构化、架构选型和核心服务的设计评审，主要工作包括：确定采用微服务而不是继续扩展单体；按业务能力划分服务边界和数据所有权；选定同步调用与异步消息的分工；组织分布式事务、限流削峰和链路观测方案，并在联调阶段根据调用链数据调整过细的拆分。开发按服务分给四个小组，我负责跨服务接口、公共技术约定和上线检查，不承担具体业务页面的编码。

### 二、微服务架构的优缺点与设计原则

微服务架构把一个应用拆成一组小服务。每个服务围绕一项业务能力构建，运行在独立进程中，拥有自己的数据，通过轻量级机制协作，并且可以单独部署、单独伸缩。它针对的是单体在变更频率和扩展粒度上的限制，不是把模块换成远程调用就自动成立。

优点主要有四点。第一，独立部署。结算规则调整只发布结算服务，任务调度和设备接入不受影响，发布窗口从整包停机变成单个服务的滚动更新。第二，独立伸缩。轨迹写入是作业季的热点，只增加轨迹服务实例，不必把门户和结算一起扩容。第三，故障隔离。设备接入抖动时，熔断之后任务查询仍可返回已落库的状态，而不是整站不可用。第四，团队边界清晰。每个小组对一个或少数几个服务的接口、库表和故障负责，减少了多人同时改同一代码库的冲突。技术栈也可以按数据特点选择，例如空间查询用支持地理类型的关系数据库，轨迹点用写入成本更低的存储，而不必强行共用一个库。

缺点同样具体。服务一拆，进程内调用变成网络调用，延迟和失败都要单独处理。数据不再由一个本地事务包住，任务完成和结算入账会出现短暂不一致。测试要覆盖服务之间的协议。运维对象从一台应用变成网关、注册配置、多个实例和消息中间件，没有自动化发布和链路追踪就很难定位故障。拆分不当时，一次查询要串起多个服务，延迟和耦合比单体更高。因此它适合业务边界已经比较清楚、各部分变更节奏不同、并且团队能独立交付的系统。

结合上述取舍，本项目在设计时遵守了下面几条原则。

围绕业务能力划分，而不是按技术分层划分。不设一个单独的“数据库服务”或“工具服务”供所有人调用，而是让任务服务拥有任务状态，结算服务拥有账单，地块服务拥有地块档案。一个需求的主要改动应尽量落在一个服务内。

每个服务独占自己的数据。其他服务需要数据时走接口或订阅事件，不跨库连接表。这样结算口径的表结构变化不会锁住轨迹库。

服务之间优先使用轻量、无状态的同步调用完成查询，用异步消息完成通知和削峰。能在一个服务内完成的业务规则不拆成远程调用。

为失败而设计。调用方设置超时、有限次重试和熔断；写入侧保证同一业务键重复投递不会产生第二张结算单。

配套自动化。服务必须能独立构建、独立发布，并带有健康检查和调用链标识，否则独立部署只停留在图纸上。

### 三、项目中的设计与实施中的问题

服务边界按业务能力收成七个：用户与权限、地块、作业任务、设备接入、轨迹与质量、结算、消息通知。对外只暴露 API 网关。浏览器和调度客户端走网关的 HTTPS 接口；装备侧走接入服务的长连接，不直接访问内部服务。每个服务独立数据库。地块服务使用带空间索引的关系数据库，轨迹服务使用适合追加写入的存储，其余服务使用常规关系数据库。服务注册与配置集中管理，同步调用经声明式 HTTP 客户端，跨服务的状态通知经消息队列。

一次作业的路径是：调度员在任务服务创建任务并绑定地块和装备；接入服务鉴权后把轨迹点写入消息队列；轨迹与质量服务消费后按地块边界计算覆盖；任务完成后发出事件，结算服务按当时的补贴规则生成结算单，再由消息服务通知农户。调度员查看进度时，网关只把请求转到任务服务，任务服务仅在需要地块名称时调用地块服务，不把轨迹点同步拉回。

实施中有三个问题比较典型。

第一个是任务完成与结算入账的一致性。最初有人希望用跨服务的分布式事务把“任务置完成”和“生成结算单”锁在一起。两条业务的库不同、处理时间也不同，结算还要读取规则表，全局事务会把任务库和结算库的锁时间拉长，作业高峰时任务更新明显变慢。我们改成基于消息的最终一致：任务服务在本地事务中同时更新任务状态和一张待发送事件表，后台按事件表投递完成事件，结算服务以任务编号为幂等键生成结算单。结算失败则消息重试；超过次数进入人工核对队列，而不是回滚已经完成的作业事实。农户端在结算单生成前看到的是“作业已完成、费用核算中”。上线后未再出现同一任务两张结算单，核算延迟在正常情况下不超过一分钟。

第二个是作业高峰的上报流量。上午开工的半小时内，大量装备同时上线并补传轨迹，接入服务的线程和轨迹库的写入一起被打满，同步调用质量计算又把延迟传回接入侧，装备开始重复上报。处理办法是把接入和计算拆开：接入服务只做鉴权、校验和入队，随即应答装备；队列按装备编号分区，保证同一台装备的点按顺序被消费；质量计算在消费端进行，落后时只增加消费者，不增加装备侧的等待。网关和接入服务对单台装备做速率限制，超过部分要求装备本地缓存后补传。改造之后，开工高峰的接入成功率稳定，轨迹服务的实例数可以按队列堆积单独增加。

第三个是拆分过细。设计初期把“作业质量”又拆成覆盖率、重复率和漏作率三个服务，一次质量查询要三次远程调用，超时后任务页面经常只显示部分指标。从调用链上看，这三个计算共享同一次轨迹读取和同一块地块边界，分开之后没有人能独立发布其中之一而不牵动另外两个。我们将三者并回轨迹与质量服务，对外只保留一个质量结果接口，内部仍按三个计算步骤组织代码。合并之后该查询的远程跳数从四跳降到一跳，页面超时明显减少。这次调整也反过来确认了划分原则：随一次业务操作同时变化、并共享同一份数据的逻辑，应放在同一个服务里。

对外接口经网关统一认证，内部调用传递追踪标识。熔断只加在强依赖的同步调用上，消息消费靠重试和死信队列，避免把积压消息直接丢掉。

上线后，结算规则在作业季调整过两次，都只发布了结算服务。轨迹服务在高峰单独扩容，其余服务实例数不变。任务完成到结算单可见的延迟可接受，未再出现单一模块故障导致全站不可用的情况。若重新划分，仍会按业务能力和数据所有权切分，并在第一次拆分时就用调用链检查同步跳数。微服务的收益来自分散发布和分散扩展，同时必须把一致性、流量和观测设计好。
